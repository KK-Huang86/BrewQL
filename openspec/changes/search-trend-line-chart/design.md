## Context

第一張圖表與第一批行為資料。資料只用模擬值（不含任何真實 Find Coffee 使用者資料），圖表由後端依結果形狀決定，前端只負責畫。

## Goals / Non-Goals

**Goals:** 問「最近半年不限時的搜尋量趨勢」看到有考試季高峰的折線圖；圖表選擇規則可測、可預期。

**Non-Goals:** 長條圖、多條線（ticket 7、之後）；讓模型決定圖表類型；使用者自選圖表。

## Decisions

### D1. 搜尋紀錄以建庫當天為基準
`search_logs` 的時間 = 建庫當下 − 隨機比例 ×（建庫當下到 6 個月前的長度），所以永遠落在曆法上的 6 個月內（固定 182 天在 9 月到 3 月這類區間會超出）。每筆搜尋只指派給搜尋時已註冊的會員，合併 `users` 的問題才合理。分布形狀每次重建相同，只隨建庫日期平移，「最近半年」永遠有資料。評估的參考 SQL 在執行當下計算，不受平移影響。代價：不同日期建的資料庫，逐筆日期不同。

### D2. 考試季效應用權重產生
5、6、11、12 月的搜尋，`filters` 同時含「不限時」與「插座」的機率較高。`filters` 只放使用者勾選的條件，鍵為布林：`no_time_limit`（不限時）、`has_socket`（有插座）、`pet_friendly`（寵物友善），例如 `{"no_time_limit": true, "has_socket": true}`；工作友善的搜尋以 `filters @> '{"no_time_limit": true, "has_socket": true}'` 判斷。任何 6 個月的區間都同時含考試季與非考試季月份，所以檢查永遠可比較。

### D3. 圖表由後端依結果形狀決定
規則確定、可單元測試，也不多花模型 token。`chart` 放在 API 回應，前端看到不認得的類型就只顯示表格。

### D4. x 軸接受 ISO 格式文字
模型常用 `to_char(..., 'YYYY-MM')` 產生月份（例如評估的 q09）。只接受 `YYYY-MM` 與 `YYYY-MM-DD` 兩種固定格式，其他文字（行政區名稱）仍是表格。

### D5. 新資料表進白名單與唯讀角色
`users`、`search_logs`、`v_daily_activity` 加入 SQL 防護白名單，`genbi_reader` 只授予 SELECT。schema 說明補欄位意義與時間用語：「最近一週」= 7 天、「最近一個月」= 30 天、「最近半年」= 6 個月，以今天往回算，模型不需要反問（「熱門」這類指標不明的問題仍反問，q15）。`search_logs.created_at` 加索引，趨勢查詢依時間篩選。CI 在 seed 後執行 `db/checks/run.sh`，故事被改壞時擋下。

### D6. 輸入 Guardrail 只擋 prompt attack
實測（4.2 前）「最近半年每個月不限時的搜尋量」被輸入 Guardrail 以 `topic:off-topic` 擋下。改了兩次拒絕話題定義都無效：版本 2 改成「不是 Find Coffee 營運數據（咖啡店、會員、搜尋）的請求」，版本 3 改成正面列舉要擋的類型（創作、閒聊、寫程式…）。直接對版本 3 送 6 種問法，凡是含「搜尋」的都被擋（「每個月有幾次搜尋？」「大安區有幾次搜尋？」），不含的都通過，與定義用字無關。

決定：拿掉 off-topic 拒絕話題，Guardrail 只保留 prompt attack 偵測（真正的安全價值在這裡）。寫詩、閒聊等無關問題由模型以 refuse 拒答（refuse-and-clarify 已有此規則），仍是兩層防護，只是拒答來源從 `input_guardrail` 變成 `model`。評估判斷拒答題不看來源（eval-golden-set D8），不受影響。附帶效果：每次檢查不再計 topic units，Guardrail 費用約減半。之後加資料表（收藏）也不會被主題分類器誤擋。擋下時的訊息改為「內容疑似要求改變系統的指示或角色」，因為現在只擋這一類。Guardrail 是 AWS 服務，單元測試不呼叫；行為由評估驗證（q14 由 Guardrail 擋下，q12、q13 由模型拒答，q16～q18 含「搜尋」都通過）。`input_guard.py` 仍解析 topic 原因，之後若再加拒絕話題不必改程式。

## Risks / Trade-offs

- [模型用 `date_trunc` 回傳 timestamp 或用文字月份] → 兩者都畫成折線圖（D4）
- [`v_daily_activity` 的「今天」用資料庫時區（UTC），應用以台北時間為準] → 午夜附近最後一天可能差一天；改資料庫時區會讓既有咖啡店資料的時間平移 8 小時，暫不處理
- [建庫日期不同造成數字不同] → 故事檢查只驗證規模與比例，不驗證逐筆數值
